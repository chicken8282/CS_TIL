# REST API 설계: 내부 구현 관점

- **리소스 중심 모델링**: URL은 동작보다 리소스를 표현하고, HTTP 메서드로 행위를 구분한다.
- **일관된 계약**: 상태 코드, 응답 형식, 오류 구조, 페이지네이션을 표준화해야 클라이언트와 서버를 독립적으로 변경할 수 있다.
- **서버 내부 흐름 고려**: 라우팅 이후 인증·검증·트랜잭션·저장소 호출·직렬화가 안정적으로 연결되어야 한다.

## 개념 설명

REST API는 단순히 `GET`, `POST`를 사용하는 규칙이 아니라, 클라이언트가 리소스의 표현을 주고받는 인터페이스다. 예를 들어 사용자는 `/users/42`라는 리소스로 식별하고, `GET`은 조회, `PATCH`는 부분 수정, `DELETE`는 삭제를 의미한다. `/getUser`처럼 URL에 동작을 넣으면 HTTP 의미와 API 규칙이 중복된다.

내부적으로 요청은 보통 **라우터 → 미들웨어 → 컨트롤러 → 서비스 → 리포지터리 → 데이터베이스** 순서로 처리된다. 라우터는 경로와 메서드를 매칭하고, 미들웨어는 인증 토큰 검증과 요청 로깅을 담당한다. 컨트롤러는 HTTP 입출력만 처리하며, 업무 규칙은 서비스 계층에 둬야 테스트와 재사용이 쉬워진다. 리포지터리는 SQL이나 ORM 세부사항을 숨긴다.

입력 검증은 컨트롤러 진입부에서 수행하고, 검증 실패는 `400`, 인증 실패는 `401`, 권한 부족은 `403`, 리소스 부재는 `404`, 충돌은 `409`로 구분한다. 성공 응답도 `200`, 생성은 `201`, 본문 없는 삭제는 `204`처럼 일관되게 선택한다. 오류는 `code`, `message`, `details` 같은 고정된 구조로 반환하면 클라이언트의 예외 처리가 단순해진다.

`PUT`은 전체 교체, `PATCH`는 부분 변경으로 정의하고, 재시도 가능한 작업은 멱등성을 고려한다. 결제처럼 중복 실행이 위험한 요청에는 `Idempotency-Key`를 저장해 동일 키의 재처리를 방지한다. 목록 API는 `limit`, 커서 기반 `cursor`를 사용하고, 응답에 다음 페이지 정보를 포함한다. 또한 데이터베이스 트랜잭션 범위, 캐시 무효화, 권한 검사를 서비스 계층에서 함께 설계해야 실제 장애를 줄일 수 있다.

```javascript
app.patch("/users/:id", auth, validateUser, async (req, res, next) => {
  try {
    const user = await userService.update(
      req.params.id, req.body, req.user.id
    );
    if (!user) return res.status(404).json({ code: "USER_NOT_FOUND" });
    res.status(200).json({ data: user });
  } catch (err) {
    next(err);
  }
});
```

## 면접 질문

### 1. `PUT`과 `PATCH`의 차이는 무엇인가?

`PUT`은 리소스 전체를 교체하는 의미이고, `PATCH`는 일부 필드만 수정하는 의미다. `PUT`은 같은 요청을 여러 번 수행해도 결과가 같아야 하는 멱등 연산으로 설계한다.

### 2. 컨트롤러와 서비스 계층을 분리하는 이유는?

컨트롤러에 업무 로직을 넣으면 HTTP 프레임워크와 결합되어 테스트와 재사용이 어려워진다. 컨트롤러는 변환과 상태 코드만 담당하고, 서비스는 트랜잭션과 도메인 규칙을 담당하게 분리한다.

> **한 줄 정리:** 좋은 REST API는 예쁜 URL보다 일관된 HTTP 계약과 계층별 책임 분리가 핵심이다.
