# MVCC(Multi-Version Concurrency Control)

- **핵심:** 읽기 작업과 쓰기 작업이 서로를 불필요하게 차단하지 않도록 행의 여러 버전을 관리한다.
- **현업 효과:** 주문 조회, 피드 조회처럼 읽기가 많은 서비스에서 락 경합과 지연을 줄인다.
- **주의점:** 오래 열린 트랜잭션은 과거 버전 정리를 방해해 저장 공간 증가와 성능 저하를 유발한다.

## 개념 설명

MVCC는 데이터를 수정할 때 기존 행을 즉시 덮어쓰는 대신, 새 버전을 생성하고 각 트랜잭션이 볼 수 있는 버전을 판단하는 방식이다. 트랜잭션은 보통 시작 시점의 스냅샷 또는 커밋된 버전만 읽으므로, 다른 트랜잭션이 변경 중인 데이터를 읽다가 깨진 결과를 보는 문제를 줄인다.

예를 들어 PostgreSQL은 행에 생성 트랜잭션과 삭제 트랜잭션 정보를 기록한다. `UPDATE`는 기존 행을 무효화하고 새 행 버전을 만든다. 이후 `VACUUM`이 더 이상 필요하지 않은 버전을 정리한다. MySQL InnoDB는 변경 전 값을 Undo 로그에 보관해 일관된 읽기를 제공한다.

현업에서는 재고 차감이나 결제 상태 변경처럼 충돌이 중요한 쓰기 작업에 조건부 갱신을 함께 사용한다. 단순 조회는 MVCC 덕분에 읽기 락을 최소화할 수 있지만, 같은 재고를 동시에 차감할 때는 `재고 >= 차감량` 조건, 비관적 락, 낙관적 버전 검사를 적용해야 한다. MVCC가 모든 경쟁 상태를 자동으로 해결하는 것은 아니다.

격리 수준에 따라 관찰 결과도 다르다. `READ COMMITTED`는 문장마다 최신 커밋 스냅샷을 사용하고, `REPEATABLE READ`는 트랜잭션 동안 동일한 스냅샷을 유지한다. 격리 수준이 높을수록 일관성은 좋아질 수 있지만 충돌, 재시도, 처리량 저하가 커질 수 있다.

운영에서는 긴 트랜잭션, 커넥션 풀에서 반환되지 않은 트랜잭션, 대량 업데이트를 특히 점검한다. 이들은 MVCC 가비지를 누적시켜 테이블 팽창, 인덱스 비효율, 디스크 사용량 증가를 일으킨다. 모니터링 지표로 트랜잭션 지속 시간, Dead tuple, Undo 공간, lock 대기 시간을 확인한다.

## 코드 예시

```sql
-- 두 요청이 동시에 재고 1개를 차감해도 음수가 되지 않게 함
BEGIN;

UPDATE product
SET stock = stock - 1,
    version = version + 1
WHERE id = 10
  AND stock >= 1
  AND version = 7;

-- 영향받은 행이 1개인지 확인
-- 0개면 재고 부족 또는 다른 트랜잭션의 선점이므로 재시도
COMMIT;
```

## 면접 질문

### 1. MVCC를 사용하는 이유는 무엇인가?

읽기와 쓰기의 충돌을 줄여 동시 처리량을 높이고, 읽는 트랜잭션이 일관된 스냅샷을 보도록 하기 위해서다. 단, 쓰기 충돌 자체를 없애지는 않는다.

### 2. MVCC 환경에서 긴 트랜잭션이 왜 문제인가?

오래된 스냅샷이 필요하므로 과거 행 버전이나 Undo 로그를 즉시 제거할 수 없다. 그 결과 테이블 팽창, 정리 작업 지연, 디스크 사용량 증가가 발생한다.

**한 줄 정리:** MVCC는 읽기 확장성을 높이는 기반 기술이며, 쓰기 충돌 제어와 짧은 트랜잭션 설계가 함께 필요하다.
