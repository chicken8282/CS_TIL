# HTTP/2 vs HTTP/3: 현업 적용과 선택 기준

- **HTTP/2**는 TCP 위에서 멀티플렉싱과 헤더 압축을 제공해 대부분의 웹 서비스 기본값으로 적합하다.
- **HTTP/3**는 QUIC과 UDP를 사용해 연결 수립 시간을 줄이고, 패킷 손실 시 TCP 수준의 전송 지연을 피한다.
- 실무에서는 전면 전환보다 **HTTP/2를 기본으로 유지하면서 CDN·로드밸런서에서 HTTP/3를 선택적으로 활성화**하는 방식이 안전하다.

## 개념 설명

HTTP/2는 하나의 TCP 연결에서 여러 요청과 응답을 스트림 단위로 동시에 처리한다. HTTP/1.1의 요청별 연결 또는 애플리케이션 레벨 파이프라이닝보다 효율적이며, HPACK으로 중복 헤더도 줄인다. 다만 TCP는 패킷 순서를 보장하므로, 한 패킷이 유실되면 해당 연결의 모든 스트림이 잠시 대기하는 **TCP Head-of-Line(HOL) Blocking**이 발생한다.

HTTP/3는 HTTP 의미 체계는 유지하면서 전송 계층을 QUIC으로 바꾼 프로토콜이다. QUIC은 UDP 위에서 동작하지만 TLS 1.3을 기본 포함하고, 연결 설정 과정에서 암호화와 전송 연결을 함께 수립한다. 스트림별로 손실을 처리하므로 이미지 하나의 패킷 손실이 다른 API 응답까지 막지 않는다. 네트워크 변경 시 연결 ID를 활용해 모바일 Wi-Fi 전환에도 연결을 유지하기 쉽고, 0-RTT 재연결도 지원한다.

현업에서는 모바일 앱, 해외 사용자, 불안정한 무선망, 대용량 이미지·동영상 서비스에서 HTTP/3 효과가 크다. 반면 UDP 차단망, 오래된 프록시, 사내 보안 장비에서는 실패할 수 있으므로 `Alt-Svc` 기반 협상과 HTTP/2 폴백이 필요하다. Nginx, Envoy, 클라우드 로드밸런서와 CDN의 QUIC 지원 여부를 확인하고, 성공률·핸드셰이크 시간·TTFB·재전송률을 지역별로 비교해야 한다. 내부 서비스 간 통신은 방화벽과 운영 복잡성을 고려해 HTTP/2 또는 기존 TCP를 유지하는 경우가 많다.

```bash
# HTTP/2 강제 확인
curl --http2 -I https://example.com

# HTTP/3 시도: 서버와 curl이 QUIC을 지원해야 함
curl --http3 -I https://example.com
```

## 인터뷰 질문

1. **HTTP/3가 HTTP/2보다 빠른 이유는 무엇인가요?**  
   QUIC 기반의 빠른 연결 수립과 스트림 단위 손실 처리를 사용해 TCP HOL Blocking을 줄이기 때문이다. 단, 모든 환경에서 항상 빠른 것은 아니며 네트워크 조건에 좌우된다.

2. **HTTP/3를 도입할 때 무엇을 검증해야 하나요?**  
   CDN·로드밸런서·클라이언트의 지원, UDP 방화벽 정책, HTTP/2 폴백, 지역별 성공률과 지연 시간을 검증해야 한다. 단순히 프로토콜 활성화만으로 성능 개선을 판단하면 안 된다.

**한 줄 요약:** HTTP/2는 안정적인 기본값이고, HTTP/3는 불안정한 네트워크와 글로벌 트래픽에서 선택적 도입 가치가 큰 진화형 프로토콜이다.
