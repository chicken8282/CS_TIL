# 해시 테이블: 평균 O(1)의 함정과 실무 트러블슈팅

- **핵심 1:** 키를 해시 함수로 버킷 위치에 매핑해 평균적으로 빠른 조회·삽입·삭제를 제공한다.
- **핵심 2:** 충돌, 높은 로드 팩터, 잘못된 키 설계가 성능 저하와 장애의 주요 원인이다.
- **핵심 3:** 장애 시 해시 분포, 리사이징, 키의 불변성, 메모리 사용량을 함께 확인해야 한다.

## 개념 설명

해시 테이블은 `hash(key)` 결과를 배열의 인덱스로 변환해 값을 저장한다. 이상적인 경우 `get`, `put`, `delete`는 평균 `O(1)`이지만, 최악에는 여러 키가 같은 버킷에 몰려 `O(n)`까지 느려질 수 있다.

충돌 해결 방식은 대표적으로 **체이닝**과 **개방 주소법**이 있다. 체이닝은 버킷마다 연결 리스트나 트리를 두고 충돌 항목을 저장한다. 개방 주소법은 다른 빈 슬롯을 탐색한다. 구현에 따라 캐시 지역성, 메모리 오버헤드, 삭제 처리 방식이 달라진다.

실무에서 가장 흔한 문제는 **로드 팩터 증가**다. 저장 항목 수가 버킷 수에 비해 많아지면 충돌이 늘어난다. 임계치를 넘으면 더 큰 배열을 할당하고 모든 키를 다시 배치하는 리해시가 발생한다. 이 작업은 순간적으로 CPU와 메모리를 크게 사용하므로, 트래픽 급증 시 지연이나 GC를 유발할 수 있다.

키는 반드시 해시와 동등성 비교 규칙이 일관되어야 한다. 특히 키 객체를 삽입한 뒤 내부 필드를 변경하면, 같은 객체처럼 보여도 기존 위치를 찾지 못할 수 있다. 캐시 장애에서는 직렬화 형식, 대소문자, 공백, 버전이 달라져 동일한 논리 키가 여러 키로 저장되는 문제도 자주 발생한다.

트러블슈팅 시에는 조회 지연 시간, 충돌 횟수, 로드 팩터, 리사이징 횟수, 메모리 사용량을 관찰한다. 분산 캐시라면 단순히 서버 수를 늘릴 때 키가 대량으로 다른 서버로 이동하는지도 확인한다. 이 경우 일관된 해싱을 사용하면 재배치 범위를 줄일 수 있다. 외부 입력을 키로 직접 사용한다면 해시 충돌 공격과 비정상적으로 긴 키도 고려해야 한다.

## 코드 예시

```python
class HashTable:
    def __init__(self, size=4):
        self.buckets = [[] for _ in range(size)]

    def _bucket(self, key):
        return self.buckets[hash(key) % len(self.buckets)]

    def put(self, key, value):
        bucket = self._bucket(key)
        for i, (k, _) in enumerate(bucket):
            if k == key:
                bucket[i] = (key, value)
                return
        bucket.append((key, value))

    def get(self, key):
        for k, value in self._bucket(key):
            if k == key:
                return value
        raise KeyError(key)
```

## 면접 질문

### 1. 해시 테이블의 평균 조회 복잡도가 O(1)인 이유는?

해시 함수가 키를 버킷에 균등하게 분배하고, 해시값으로 접근 위치를 바로 계산하기 때문이다. 단, 충돌이 과도하면 최악의 경우 `O(n)`이 된다.

### 2. 로드 팩터가 높아지면 어떤 문제가 생기며 어떻게 해결하는가?

버킷당 항목 수와 충돌이 증가해 조회가 느려진다. 더 큰 테이블을 할당하고 리해시하며, 임계치와 초기 용량을 적절히 설정한다.

## 한 줄 정리

**해시 테이블은 빠르지만, 충돌·리사이징·키 불변성·분포를 관리해야 실무에서도 안정적이다.**
