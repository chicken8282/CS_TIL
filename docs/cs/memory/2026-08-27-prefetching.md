# Prefetching: 필요하기 전에 데이터를 가져오는 전략

- **핵심:** 실제 사용 시점보다 먼저 데이터·명령어·파일을 캐시로 가져와 지연 시간을 줄인다.
- **효과:** 네트워크 왕복, 디스크 접근, DB 조회, CPU 캐시 미스 비용을 사용자 요청 전에 숨길 수 있다.
- **위험:** 사용하지 않는 데이터를 가져오면 대역폭·메모리·DB 커넥션을 낭비하고, 잘못된 예측은 오히려 성능을 악화시킨다.

## 개념 설명

Prefetching은 “다음에 필요할 가능성이 높은 자원”을 미리 읽는 최적화다. CPU는 순차 메모리 접근을 예측해 캐시에 적재하고, 브라우저는 링크·이미지·DNS·API를 미리 요청한다. 서버 애플리케이션에서는 다음 페이지 데이터, 추천 목록, 자주 조회되는 레코드를 미리 읽을 수 있다.

실무에서는 **무엇을, 언제, 얼마나 미리 가져올지**가 중요하다.

- **대상:** 높은 확률로 사용되며, 가져오는 비용이 큰 데이터
- **시점:** 사용자 행동 신호가 충분히 나타난 뒤. 예를 들어 링크에 마우스를 올리거나 다음 페이지로 스크롤하기 직전
- **범위:** 전체 목록보다 필요한 일부 필드·첫 페이지만 요청
- **캐시 정책:** TTL, 최대 크기, 무효화 조건을 함께 설계

트러블슈팅 시에는 먼저 “빨라졌는가”보다 **실제 적중률과 비용**을 측정한다. `prefetch 요청 수`, `실제 사용된 비율`, `캐시 적중률`, `요청 취소율`, `p95 지연 시간`, `대역폭·DB QPS 증가량`을 분리해 본다. 적중률이 낮으면 예측 조건을 좁히고, QPS가 증가하면 TTL·동시성 제한·배치 조회를 검토한다.

Prefetching 때문에 장애가 발생하면 네트워크 탭에서 요청 폭증과 중복 요청을 확인하고, 캐시 키가 사용자·권한·지역별로 안전하게 분리됐는지 점검한다. 오래된 데이터를 보여주는 문제는 캐시 무효화와 응답 버전을 확인한다. 모바일 환경에서는 `Save-Data`, 느린 네트워크, 배터리 상태를 고려해 기능을 끄는 것이 안전하다.

```javascript
const controller = new AbortController();

function prefetch(url) {
  return fetch(url, {
    signal: controller.signal,
    headers: { "X-Prefetch": "true" }
  }).then(r => r.ok ? r.json() : Promise.reject(r.status));
}

link.addEventListener("mouseenter", () => {
  if (!cache.has("/next")) prefetch("/next").then(v => cache.set("/next", v));
});
link.addEventListener("mouseleave", () => controller.abort());
```

## 면접 질문

### 1. Prefetching과 lazy loading의 차이는?

**답:** Prefetching은 미래 사용을 예측해 미리 가져오는 방식이고, lazy loading은 실제 필요 시점까지 로딩을 지연하는 방식이다. 전자는 지연 시간을 줄이지만 낭비가 생길 수 있고, 후자는 초기 비용을 줄이지만 사용 순간 지연이 발생할 수 있다.

### 2. Prefetching이 성능을 악화시키는 경우는?

**답:** 예측 적중률이 낮거나, 큰 리소스를 과도하게 요청하거나, 캐시 미스·중복 요청·DB 부하를 유발할 때다. 적중률과 비용을 측정하고 요청 범위, TTL, 동시성, 네트워크 조건을 조정해야 한다.

> **한 줄 요약:** Prefetching은 “미리 가져오기”가 아니라, 적중률과 비용을 측정하며 지연 시간을 숨기는 예측 기반 최적화다.
