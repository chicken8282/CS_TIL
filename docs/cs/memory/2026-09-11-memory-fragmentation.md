# 메모리 단편화

## 핵심 요약

- **외부 단편화**: 여유 메모리는 충분하지만 작은 조각으로 흩어져 큰 연속 영역을 할당하지 못하는 현상이다.
- **내부 단편화**: 할당 단위나 정렬 때문에 요청한 크기보다 더 많은 공간을 차지하는 현상이다.
- 현업에서는 장시간 실행되는 서버의 **RSS 증가, 할당 실패, GC 부담, 컨테이너 OOM**으로 관찰되며, 할당 전략과 수명 관리로 완화한다.

## 개념 설명

메모리 단편화는 사용과 해제를 반복하면서 메모리 공간의 배치가 비효율적으로 변하는 문제다. 예를 들어 100MB를 여러 블록으로 나눈 뒤 중간 블록만 해제하면 총 여유 공간은 충분해도 40MB짜리 연속 공간을 확보하지 못할 수 있다. 이것이 외부 단편화다.

내부 단편화는 메모리 관리자가 최소 블록 크기, 정렬, 페이지 단위 등을 적용하면서 발생한다. 13바이트를 요청해도 16바이트 또는 더 큰 클래스가 사용될 수 있다. 객체가 작고 많을수록 낭비 비율이 커진다.

현업에서는 다음 사례가 흔하다.

- **C/C++ 장기 실행 프로세스**: 다양한 크기의 객체를 반복 할당·해제하면 힙이 조각나고, 실제 사용량보다 RSS가 크게 유지될 수 있다.
- **웹 서버와 캐시**: 요청마다 임시 버퍼를 만들면 크기 변화가 커져 단편화가 누적된다.
- **JVM/.NET 서비스**: GC가 살아 있는 객체를 이동시켜 외부 단편화를 줄이지만, 큰 객체 영역이나 네이티브 메모리는 별도 관리가 필요하다.
- **컨테이너 환경**: 애플리케이션이 메모리를 논리적으로 해제해도 allocator가 OS에 반환하지 않으면 cgroup 관점의 RSS가 줄지 않아 OOM이 발생할 수 있다.

대응 방법은 객체 크기별 풀·슬랩 allocator 사용, 요청 버퍼 재사용, 임시 객체의 수명 통일, 큰 객체의 별도 영역 관리다. Linux에서는 `malloc_trim`이 일부 여유 공간을 OS에 반환할 수 있지만 성능 저하가 생길 수 있다. 측정 시에는 heap 사용량만 보지 말고 RSS, allocator 통계, 할당 크기 분포, GC 시간, 페이지 반환 여부를 함께 확인해야 한다.

```c
#include <stdlib.h>

int main(void) {
    void *blocks[1000];

    for (int i = 0; i < 1000; i++)
        blocks[i] = malloc((i % 7 + 1) * 24);

    for (int i = 0; i < 1000; i += 2)
        free(blocks[i]);          // 중간 공간이 조각으로 남음

    void *large = malloc(1000 * 24); // 총 여유량과 연속 공간은 다름
    free(large);
    for (int i = 1; i < 1000; i += 2)
        free(blocks[i]);
}
```

## 면접 질문

### 1. 외부 단편화와 내부 단편화의 차이는?

외부 단편화는 여유 공간이 여러 조각으로 흩어지는 문제이고, 내부 단편화는 할당된 블록 내부의 사용되지 않는 공간이 늘어나는 문제다.

### 2. 메모리를 `free`했는데 RSS가 줄지 않는 이유는?

allocator가 재사용을 위해 페이지를 보유하거나, 페이지 일부가 아직 사용 중이라 OS에 반환하지 못하기 때문이다. RSS와 실제 라이브 객체 크기는 다를 수 있다.

## 한 줄 정리

메모리 단편화는 단순한 누수와 다르며, **할당 패턴·객체 수명·allocator 동작·RSS를 함께 분석해야 해결할 수 있다.**
