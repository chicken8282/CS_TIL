# 프롬프트 엔지니어링: 실수와 안티패턴

- **목표·대상·출력 형식**을 명시해야 모델의 응답 편차가 줄어든다.
- 모호한 지시, 과도한 정보, 검증 없는 생성은 대표적인 실패 원인이다.
- 한 번에 완벽한 프롬프트를 만들기보다 **작게 실험하고 평가 기준으로 개선**한다.

## 개념 설명

프롬프트 엔지니어링은 LLM이 원하는 작업을 안정적으로 수행하도록 입력을 설계·검증하는 방법이다. 핵심은 “무엇을 해라”보다 **어떤 맥락에서, 어떤 제약으로, 어떤 형태로 결과를 낼지**를 구체화하는 것이다.

좋은 프롬프트는 보통 다음 요소를 포함한다.

1. **역할과 목표**: 모델의 관점과 해결할 문제를 정의한다.
2. **입력 데이터**: 분석 대상과 데이터의 경계를 명확히 한다.
3. **제약 조건**: 언어, 길이, 금지 사항, 대상 독자를 지정한다.
4. **출력 스키마**: JSON 필드, 표, 단계 목록처럼 결과 형식을 고정한다.
5. **검증 기준**: 누락 여부, 근거 포함 여부, 불확실성 표시 방법을 정한다.

자주 하는 실수는 “알아서 잘 작성해 줘”처럼 성공 기준을 생략하는 것이다. 역할만 길게 부여하는 것도 효과가 제한적이다. 모델의 페르소나보다 입력·출력 계약이 더 중요하다. 또한 예시를 지나치게 많이 넣으면 토큰 비용이 커지고, 예시의 오류나 편향을 그대로 학습할 수 있다. 서로 충돌하는 지시를 여러 곳에 배치하거나, 최신 사실을 근거 없이 생성하게 두는 것도 위험하다.

대표적인 안티패턴은 다음과 같다.

- **모호한 요구**: “좋은 코드로 고쳐라” → 품질 기준과 범위가 없다.
- **만능 프롬프트**: 분석, 구현, 번역, 검증을 한 요청에 섞는다.
- **출력 형식 미지정**: 파싱이 필요한데 자연어 응답을 허용한다.
- **검증 생략**: 모델의 답을 사실로 간주하고 테스트하지 않는다.
- **비밀정보 삽입**: API 키, 개인정보, 내부 소스가 프롬프트에 노출된다.
- **프롬프트 인젝션 방어 부족**: 외부 문서의 지시를 시스템 규칙처럼 따른다.

실무에서는 작업을 단계로 분리하고, 구조화된 출력과 자동 검증을 함께 사용한다. 검색 결과나 사용자 문서는 “참고 데이터”로 취급하며, 그 안의 지시는 실행하지 않도록 경계를 명시해야 한다.

```python
prompt = f"""
역할: 숙련된 Python 리뷰어
목표: 아래 함수의 버그와 성능 문제를 찾는다.
입력:
{code}
제약:
- 추측하지 말고 근거를 줄 것
- 심각도를 high/medium/low로 표시
출력(JSON):
{{"issues": [{{"severity": "...", "line": 0, "reason": "...", "fix": "..."}}]}}
"""
```

## 인터뷰 질문

**Q1. 프롬프트에 예시를 넣는 이유와 부작용은?**  
A. 원하는 입출력 패턴을 직접 보여주기 위해서다. 다만 예시가 틀리거나 편향되면 모델이 이를 모방하며, 토큰 비용도 증가한다.

**Q2. 프롬프트 인젝션을 어떻게 줄이는가?**  
A. 외부 데이터를 지시와 분리하고, 신뢰할 수 있는 규칙을 상위 메시지에 둔다. 허용된 도구·출력만 사용하게 하며 결과를 스키마와 정책으로 검증한다.

> **한 줄 정리:** 좋은 프롬프트는 장황한 문장이 아니라 명확한 목표, 제약, 출력 계약과 검증 절차의 조합이다.
